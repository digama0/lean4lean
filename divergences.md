# Divergences from the Lean Kernel

This is a list of places where lean4lean deliberately has different behavior from the kernel. Unless specified here, any divergence between lean4lean and [lean4](https://github.com/leanprover/lean4/tree/master/src/kernel) is a bug.

* [`Lean4Lean.TypeChecker.Inner.reduceNative`](Lean4Lean/TypeChecker.lean): Lean4lean does not support reduction of `reduceBool`. This would involve implementing verified compilation, which while possible would be an additional chunk of work comparable to this entire repo.
* [`Lean4Lean.Primitive.checkDef`](Lean4Lean/Primitive.lean), `checkInductive`: Lean does not check that primitives are declared with the correct types and definitional behavior, except in the case of `Eq` which is used in the declaration of `Quot`. This is required for soundness, but Lean is able to get away with it because Lean ships its prelude and using an alternative prelude is not supported.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), literal case: The original code was not checking that the literal type actually exists. Again, this is okay provided that the prelude is trusted.
* [`Lean4Lean.TypeChecker.Inner.tryStringLitExpansionCore`](Lean4Lean/TypeChecker.lean): there is a counterproductive `whnf` call in this function which is removed in Lean4lean.
* [`Lean4Lean.TypeChecker.Inner.isDefEqApp`](Lean4Lean/TypeChecker.lean): lean4lean compares the two argument counts before the two heads, where `type_checker::is_def_eq_app` compares the heads first. Both answer `false` when the counts differ, so the decision is the same.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), application case: lean4lean checks `isDefEq dType aType`, where `infer_app` checks `is_def_eq(a_type, d_type)`. This avoids some needless left-right flipping. What is proved: a `true` answer is sound in either order (`TypeChecker.isDefEq.WF` gives the declarative `IsDefEq` of the two translations, and that relation is symmetric), so the swap cannot make lean4lean accept an ill-typed application. What is not proved: that `isDefEq dType aType` and `isDefEq aType dType` return the same answer. The implementation is not symmetric as a computation (lazy delta reduction, the order in which eta and unit-like rules are tried, the caches, the equivalence manager and fuel all see the two sides differently), and no theorem relates a `false` answer to the declarative relation. What is tested: the fresh replays of `Init.Prelude` and `Init.Core` (and the test suite) accept everything the C++ kernel accepts. An argument that the swap never changes the decision on the C++ kernel's inputs is outstanding.
* [`Lean.Level.normalize`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Level.lean), `isEquiv`, `geq`, `instantiateLevelParams`: Lean4lean uses the level operations from Lean's standard library, which differ from the C++ kernel's; [leanprover/lean4#14356](https://github.com/leanprover/lean4/pull/14356) tracks aligning them. This has two separate consequences. The comparison operations decide slightly different sets of (in)equalities than the kernel's `is_equiv`/`is_geq` (but see the next point). And because `instantiateLevelParams` builds levels with `mkLevelMax'`/`mkLevelIMax'` rather than the kernel's `mk_max`/`mk_imax`, unfolding a universe-polymorphic constant can produce a term that means the same as the kernel's but is not syntactically equal to it, and so does not share its `Expr.hash`.
* [`Lean.Level.normalize'`](Lean4Lean/Level.lean), `isEquiv'`, `geq'`: Lean4lean implements a new algorithm for level normalization. These run the standard library's operation as a fast path and fall back to a complete decision procedure for level algebra, so lean4lean decides level equality and `≥` for *more* pairs than either the standard library or the kernel — it accepts declarations the kernel rejects for reasons of level incompleteness, never the other way around.
* [`Lean4Lean.checkConstantVal`](Lean4Lean/Environment.lean): The original implementation would call `check` which sets the level params and then unsets them afterward, and then `ensure_sort` would run in a context without any level params. In lean4lean the monad is parameterized over level params, so they remain the same across the two calls.
* [`Lean4Lean.TypeChecker.Inner.inferProj`](Lean4Lean/TypeChecker.lean), [`toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean): both kernels recognize `Prop` up to universe normalization ([leanprover/lean4#14613](https://github.com/leanprover/lean4/pull/14613)), but they differ on levels that are neither always nor never zero: lean4lean tests `isNeverZero` where Lean tests `!isAlwaysZero`. Lean4lean's rule requires the structure's universe to be never zero at the projection's particular universe instantiation. This does not make every accepted projection expressible with the exact recursor generated before specialization. For `MaybeProp.{u} : Sort u` with a field in `PUnit.{u}`, the kernel cannot rule out that the type is a proposition, so it emits `MaybeProp.rec : {motive : MaybeProp → Prop} → ...` (small elimination only), and `fun x => x.0 : MaybeProp.{u} → PUnit.{u}` cannot be written with it. Lean accepts that projection anyway, so under Lean's rule `proj` computes something the type's own eliminator cannot. Lean's choice is still sound, but only because the constructor universe bound in `inductive.cpp` separately rejects `inductive T.{u} : Sort u where mk : Bool → T`, which would otherwise give an analogue of the construction in #14613; testing `isNeverZero` makes the projection check independent of that bound. Even with this check, specializing a sort-polymorphic box to `Sort 1` permits a large projection while its recursor remains restricted to `Prop`; `Tests/ProjectionSpecialization.lean` exercises this case. Projection desugaring needs an abstract eliminator schema with admissibility checked after specialization. Reconciling the two in the other direction (letting the recursor eliminate large whenever every field's universe is bounded by the inductive's, which is exactly what makes such a projection sound) would be the complete answer, but that is a change to recursor generation rather than to this check.
* [`Lean4Lean.TypeChecker.Inner.tryEtaStructCore`](Lean4Lean/TypeChecker.lean): lean4lean only applies structure eta when the sort of the structure type is never zero, where `try_eta_struct_core` applies it to any constructor application of a non-recursive structure. When the type is a proposition, `isDefEqProofIrrel` has already decided the comparison, so the difference is confined to structures in a universe that is neither always nor never zero (`Sort u`), exactly as for `inferProj` above: there the projections `tryEtaStructCore` compares may not be well typed, and the verified checker never compares ill-typed terms. As in `try_eta_struct_core`, the constructor `f` at the head of `s` is not compared with the constructor its structure lists, nor on `isUnsafe`: every constructor of a checking environment is listed by its owner, with the owner's `isUnsafe` (`ConstructorOwnersPresent`, carried by `VContext.constructorOwners`), so the non-recursive-structure test already identifies `f` with the structure's unique constructor.
* [`Lean4Lean.toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean): `toCtorWhenStruct` leaves the term unchanged when the whnf of the type of its type is not a sort, where `to_cnstr_when_structure` expands it (it only skips a sort that normalizes to zero). The type of a type is definitionally a sort, but the verification does not establish that its whnf is syntactically one, and the expansion is only justified at a known never-zero sort (see the `isNeverZero` entry above). The number of parameters of the expansion is read from the constructor, and the arguments of the type are truncated to it, as `args.shrink(nparams)` does; the type of a well-typed term applies a structure to exactly its parameters (`VContext.structTypeArgs`), so the truncation never drops an argument on well-typed input (with too few arguments, `args.shrink` is not defined in the C++ kernel and `mkAppRange` panics in lean4lean).
* [`Lean4Lean.Environment.restoreNestedAfterInstall`](Lean4Lean/Inductive/Add.lean): the restored recursor rules are validated (`validateRestoredRecursorRules`) in a copy of the restored environment in which every restored recursor carries an empty rule list (`stripRecursorRules`), where upstream's check ([leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621)) runs in the restored environment itself. Like upstream's, the validation type-checks the right-hand side of each rule; with the rules present, iota reduction of a restored recursor could be used while its own rule is being validated, which the verification cannot justify (the abstract iota equations are only added once the rules are known to be well formed, and the translation of each right-hand side is read off this check). Stripping the rules makes the check strictly more conservative: a rule whose typing needed a sibling rule's reduction is rejected rather than accepted, and no rule the kernel generates needs one. The returned environment is unchanged.
* [`Lean4Lean.checkNoNestedAux`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14616](https://github.com/leanprover/lean4/pull/14616) rejects the reserved `_nested` prefix in both the inductive types and the constructor types of a declaration; lean4lean checks only the constructor types. The bug that check fixes is specific to constructors: nested occurrences are rewritten to the auxiliary types in constructor types only (`replaceAllNested`), and rewritten back the same way (`restoreNested`), so an inductive's own type is carried through both directions verbatim and cannot acquire a type it was not checked at. A `_nested` name written in an inductive type also cannot resolve in the first place: the auxiliary types are declared in the same block, so they are not in the environment while that block's types are checked (unlike constructor types, which are checked once the block's types, auxiliaries included, are present), and they never survive into the final environment. Lean's check additionally reserves the whole `_nested` namespace against unrelated user declarations, which lean4lean does not.
* [`Lean4Lean.ElimNestedInductive.Result.restoreNested`](Lean4Lean/Inductive/Add.lean), `restoreCtorName`: [leanprover/lean4#14632](https://github.com/leanprover/lean4/pull/14632) turned the `lean_assert`s in the nested-inductive restoration into kernel exceptions; lean4lean keeps `unreachable!` and `assert!`. The branches are unreachable: `restoreCtorName` runs only for the recursors of the auxiliary types the elimination generates, whose constructors are exactly the keys of `aux2nested`, and the nested occurrences stored there are applications of a constant by construction. Upstream's stated motivation is that the assertions vanish in a release build and the C++ consumers then read out of bounds; the corresponding accesses here are total, so there is nothing to read out of bounds. Note that if one of these invariants were broken anyway, `unreachable!` would continue with a default value rather than reject; the restored constructor and recursor types are re-checked in the final environment ([#14621](https://github.com/leanprover/lean4/pull/14621)), which lean4lean retains, but a restored rule constructor *name* is not covered by that pass.
* [`Lean4Lean.FuelConfig`](Lean4Lean/FuelConfig.lean): since [leanprover/lean4#13956](https://github.com/leanprover/lean4/pull/13956), the native kernel bounds mutually recursive checking through the `maxRecDepth` option. Lean4lean exposes several independent fuel counters instead, because its Lean definitions also need explicit termination witnesses. Replay comparison therefore uses each implementation's default bound unless an explicit lean4lean fuel configuration is supplied.
* [`Lean4Lean.addDefinition`](Lean4Lean/Environment.lean) (`unsafe` branch), [`addMutual`](Lean4Lean/Environment.lean): an `unsafe`/`partial` definition may be recursive, so its body is checked in an environment that already contains the declaration. The C++ kernel adds `constant_info(d)` there -- the full definition, value included -- so the body can delta-unfold the very constant being defined. Lean4lean adds it as an axiom of the same type instead: the body may still *refer* to the block's constants, but cannot unfold them. So for example `unsafe def foo : Nat := (fun (_ : foo = 1) => 1) rfl` is accepted by the C++ kernel, but rejected by L4L: checking the argument requires `foo =?= 1`, which succeeds by unfolding `foo` to its own body and reducing. Read literally, that rule makes a typing fact about the constant available while establishing it, and implementing this in `IsDefEq` directly degenerates completely, allowing even things like `unsafe def bar : Nat := "hi"` by using the typing judgment to justify itself. The gap is confined to `unsafe`/`partial` code, which carries no logical content.
* [`Lean4Lean.addMutual`](Lean4Lean/Environment.lean): lean4lean requires the declarations of a mutual block to carry the same universe parameters and to have distinct names. Both checks are in kernel PRs that are not yet released ([leanprover/lean4#14608](https://github.com/leanprover/lean4/pull/14608), [#14632](https://github.com/leanprover/lean4/pull/14632)); the released kernel checks only that the safety annotations agree. Lean4lean needs them rather than merely matching them: the block is checked under a single `M.run`, whose level parameters are fixed for the whole run, and the model adds the block's constants one at a time with `VEnv.addConsts`, which fails on a repeated name.
* [`Lean4Lean.TypeChecker.State.leaveScope`](Lean4Lean/TypeChecker.lean), `State.exitScope`, `withFreshId`, `isDefEqLambda`, `isDefEqForall`, [`Lean4Lean.CacheMode`](Lean4Lean/CacheMode.lean): the executable implements both behaviours, selected by the `cacheMode` field of `FuelConfig`. In the default mode, `.scoped`, every binder the checker opens puts the inference caches, the `whnf` caches, the equivalence manager and the failure cache back to their state before the binder when it is closed (the name generator stays advanced and the `unfold` cache, which depends only on the environment, is kept), and `isDefEqLambda`/`isDefEqForall` compare the bodies under a binder even when neither mentions it. In the mode `.global license` the caches and the equivalence manager are kept for the whole run and a binder is opened only when a body has loose bound variables, as in the C++ type checker (`is_def_eq_binding`), so a conversion fact established under a binder answers later queries outside it. The global mode can be selected only with a `GlobalCacheLicense`, a proof that every well-formed environment with canonical `Eq` admits context strengthening, of which no inhabitant is known; it cannot be selected from a configuration file. So the executable as run differs from the C++ kernel here, and the difference can change a decision, only towards rejection. `Lean4Lean/Tests/CacheScope.lean` builds, in an environment without `Eq`, a closed definition whose value first forces the comparison `SI ≡ SJ` under a hypothesis `q : P v` (inside an otherwise unused `let`) and then uses a term of type `SI` at type `SJ`: the C++ kernel accepts it and rejects the same definition without the seeding `let`; the scoped mode rejects both (the global mode would accept it as the C++ kernel does). `SI ≡ SJ` holds in the context extended by `q` but is not derivable in the outer context (section 5.1 of the design notes), so the C++ acceptance uses a conversion fact outside the scope in which it holds. Both modes are verified (`addDecl.WF_of_canonicalEq_mode`): the scoped mode needs every cache entry to be derivable in the current context, the global mode moves cached facts out of a binder with the strengthening the license gives for an environment with canonical `Eq`. That environment above has no `Eq`, so the license would not cover it either. Replays of `Init.Prelude` and `Init.Core` are unaffected.
* [`Lean4Lean.AddInductive.Context.checkLCtx`](Lean4Lean/Inductive/Add.lean), `withCheckLCtx`, `withCheckedLocalDecl`, `paramCheckLCtx`: the type checker runs embedded in the inductive checker see a local context holding only the parameters, indices and fields that the run's input can mention, never the majors, motives, minors or induction hypotheses that `inductive.cpp` keeps in `m_lctx`. A checker run looks up only the free variables reachable from its input, and every embedded C++ call constructs a fresh `type_checker`, so no cache is shared between calls; the decisions are the same. (A narrowing that left out a variable the input mentions would make the run fail with an unknown free variable; the replays and `Tests/RecursorOracle.lean` exercise every call site.) The narrowing lets each checker fact be produced in the scope its verification uses.
* [`Lean4Lean.ElimNestedInductive.mkUniqueName`](Lean4Lean/Inductive/Add.lean): the auxiliary types produced by nested-inductive elimination are named `_nested.1`, `_nested.2`, ... (`Name.mkNum`), where `elim_nested_inductive_fn` names them `_nested.J_1`, `_nested.J_2`, ... after the nested family `J` (`append_after`). The fresh-name search is also bounded (by the size of the environment plus one, which always suffices) instead of unbounded. The auxiliary names are internal: they are not in the returned environment, constructor and recursor names are restored from them by prefix replacement, and both kernels skip names already in the environment, so the choice of names cannot change a decision; it is visible only in error messages about auxiliary constructors. The verification relies on the numeric form to separate auxiliary family names from the string-extended names of restored declarations (`Verify/Inductive/Nested/Restoration/LoweredRuleAvoidance.lean`).
* [`Lean4Lean.AddInductive.declareRecursors.checkRecursorTypes`](Lean4Lean/Inductive/Add.lean): each generated recursor type is type-checked (in the empty local context, under the recursor's universe parameters) before the recursors are installed. The kernel of the pinned toolchain (v4.33.0-rc2) installs generated recursors with `add_core` and does not check them; [leanprover/lean4#14808](https://github.com/leanprover/lean4/pull/14808) (v4.35) adds `check_recursors`, which type-checks each recursor type after installation (the same check: a recursor type does not mention the recursors) and also checks that each computation rule is type-preserving (`whnf` of the recursor applied to a constructor has the recursor's result type). Lean4lean does not perform the rule check for ordinary blocks: the verification proves the generated rules correct instead (each installed iota equation is one of the equations of the generative specification), so it would add proof obligations without contributing an invariant. The recursor-type check is not redundant for the verification: its postcondition (`TrRecursorTypes`) is how `declareRecursors.checkRecursorTypes.trRecursorTypesWF` supplies the translation and well-typedness of the installed recursor types. On a correctly generated recursor neither check fails, so the decisions agree with both kernels except through checker fuel.
* [`Lean4Lean.AddInductive.mkRecInfos.loopArgs1`](Lean4Lean/Inductive/Add.lean), `loopInd1`, `loopUTemplates`: recursor construction throws when the normalized inductive header has fewer parameters than declared (`loopArgs1`), when it has a different number of indices than `checkInductiveTypes` recorded (`loopInd1`), and when the normalized type of a field that `isRecArg` classified as recursive does not end in a valid application of a family of the block (`loopUTemplates`). In `mk_rec_infos` the first two cases have no check at all (the header loop simply stops and keeps the indices it found) and the third is the `lean_assert(r)` of `get_I_indices`, whose `*r` is undefined in a release build. None of the throws is reachable, so the decisions and the constructed terms are the same as the C++ kernel's: each re-normalization runs `whnf` on the same expression, in a checker context holding the same variables (`paramCheckLCtx`, or the parameters and earlier fields), as the run in `checkInductiveTypes` or `isRecArg` that established the arity or the result type, up to renaming the freshly opened index and argument variables (for a field, `isRecArg` reads the domain before type-annotation wrappers are stripped, and `whnf` unfolds the prelude's wrappers). They are kept because the verification can prove neither of the two facts that would replace them. The direct fact, that two executable `whnf` runs on the same input in such contexts return the same result (independently of the caches, and equivariantly under renaming of free variables), is not a theorem. The semantic route (the checked header is definitionally a telescope of `nparams + nindices` binders ending in a sort, so a non-`forallE` result of `whnf` would be a `whnf`-normal type definitionally equal to a `forallE`) needs a separation of `forallE` from types headed by a free variable, a stuck recursor or a stuck projection, and the fact that a `whnf` result has one of these heads; `VEnv.WF.headInversion` separates only sorts, `forallE` and rigid constant heads, and `whnf` results are not characterized. Only the case of more indices than recorded follows (`IsDefEqU.sort_forallE_inv`); the recursive-field case needs the syntactic parameter equality of `isValidIndApp?`, which no definitional fact gives.
* [`Lean4Lean.AddInductive.checkRecursiveFields`](Lean4Lean/Inductive/Add.lean), `checkPositivity`, `checkConstructors`: for a safe declaration, after the minor pass the fields that receive an induction hypothesis (those `isRecArg` classifies as recursive, in the recursor's checking context and the environment with the constructors) are required to be exactly the fields the positivity check classified as recursive (in the environment with the family headers). `checkPositivity` reports the classification it already computes (a field is recursive when its weak head normal form, through family-free binders, ends in a valid family application) and `checkConstructors` returns it; `inductive.cpp` computes the classification twice and does not compare. The specification needs the agreement, because it classifies each field by its strictly positive normal form (`InductiveSignature.Models.classifiedFields`), which the positivity check certifies and `isRecArg` does not: a field given an induction hypothesis must have a recursive normal form and any other field a family-free one, and a positively recursive field left without a hypothesis has none (`Tests/RecursiveFieldClassification.lean`). The two classifications are chains of `whnf` runs, each a fresh checker run (`M.run` starts from the empty state, so no cache is shared), on the same field types up to three differences: the environment (headers alone, headers and constructors), the universe parameters (the recursor's may add the elimination universe) and the free variables (the two passes open the fields, and the binders of each field's telescope, with different identifiers of the inductive checker's name generator). The first two leave the inputs of the runs identical; the third is a renaming, and agreement under it is not provable in the model of the executable, so the comparison is kept. `whnf` consults `isDefEq` when it reduces a K-like recursor (`toCtorWhenK`), and the decisions of `isDefEq` depend on the names of free variables: `isDefEqCore'` first asks the equivalence manager with `useHash := true`, which answers `false` without consulting its union-find structure when the two hashes differ, and `Expr.hash` is not invariant under renaming (`Tests/FVarRenamingEquivManager.lean` exhibits two fresh identifiers of the generator with colliding hashes, for which the manager's answer after the same merge is `true`, and their renaming to two non-colliding identifiers, for which it is `false`); the pointer-equality tests of `isEquiv` and `isDefEqCore'` (`ptrEqExpr`) are opaque, so their answers on a term and on its renaming are unrelated in the model; and the manager's answers are not only an optimization: a conversion fact it records can decide a later comparison that the conversion check would not otherwise settle (`Tests/CacheScope.lean`, with the C++ kernel's manager, which persists across binder scopes). A semantic argument does not replace the syntactic agreement either: `isRecArg` and `isValidIndApp?` test syntactic equality of the parameters, so a field whose two normal forms are definitionally but not syntactically equal family applications is classified differently, and no definitional fact excludes it (see the `mkRecInfos.loopArgs1` entry). The C++ kernel's equivalence manager also uses hashes and pointer equality, so its two classifications can in principle differ as well; it would then generate a recursor whose induction hypotheses disagree with the strict positivity of the fields, where lean4lean rejects the declaration. No declaration on which the classifications differ is known: both fresh replays are unchanged, and `Tests/RecursorOracle.lean` compares the generated recursors with the kernel's.
* [`Lean4Lean.Environment.restoreNestedAfterInstall`](Lean4Lean/Inductive/Add.lean), `validateSourceConstructorTypes`, `validateRestoredRecursorTypes`: the re-checks of [leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621) run in side environments that contain only the restored headers (and, for the recursor types, the restored constructors), not in the complete restored environment. The verification needs these environments: the constructor check gives the telescope certificate of each restored constructor in the header environment (`validateSourceConstructorTypes.telTr_of_run`, `Verify/Inductive/Nested/Restoration/ConstructorTelescopes.lean`), and the recursor-type check gives the translation of each restored recursor type in the environment of the restored constructors, before any restored recursor is installed (`validateRestoredRecursorTypes.translation_of_check`); a check in the complete restored environment would need the validity of that environment, which is what these facts are used to prove. A type check that succeeds in a side environment succeeds in the complete one, which extends it. Conversely, restored constructor and recursor types cannot mention the restored recursors, and the definitions of the source environment cannot mention any restored constant, so the only constants of the complete environment that a check of these types can consult beyond the side environment are, for the constructor types, the restored constructors, through structure eta and unit-like conversion at a restored structure type. The ordinary pipeline checks the lowered constructor types in the lowered header environment, which lacks the constructors as well, so a declaration whose constructor types need such a conversion is rejected before restoration by both kernels.
* [`Lean4Lean.validateNestedAuxiliaries`](Lean4Lean/Inductive/Add.lean): the parametric nested applications `I Ds` of [leanprover/lean4#14577](https://github.com/leanprover/lean4/pull/14577) are type-checked, as in the C++ kernel, but in the environment of the restored headers only (the C++ kernel uses the complete restored environment; `Ds` cannot mention the block's constructors or recursors, so the decision is the same). The stored application is `I` applied to its parameters only, so for a nested occurrence of a family with indices it is a type family, not a type, and neither kernel requires a type: `inductive VTree | node : Vec VTree 2 → VTree`, with `Vec : Type → Nat → Type`, is accepted by both, with the same constructors and recursors (`Tests/NestedIndexedFamily.lean`). The verification closes each stored application with lambdas over the parameters, and its inferred type with foralls over the same parameters (`ClosedNestedOccurrencesTyped`), so it covers type families as well as types.

* [`Lean.Kernel.Environment.isTypeAnnotationWrapper`](Lean4Lean/Expr.lean), [`Lean.Expr.consumeTypeAnnotationsVerified`](Lean4Lean/Expr.lean), [`Lean4Lean.AddInductive.withUnannotatedCheckedLocalDecl`](Lean4Lean/Inductive/Add.lean): the inductive checker strips `optParam α d`, `autoParam α s`, `outParam α` and `semiOutParam α` to `α` in binder domains, as `consume_type_annotations` does in the C++ kernel (called from `local_ctx::mk_local_decl`), but only when the environment declares the name as the prelude's definition: a safe definition with universe parameters `[u]` whose type and value are exactly the prelude's (`@[reducible] def optParam (α : Sort u) (default : α) : Sort u := α`, `def autoParam (α : Sort u) (tactic : Lean.Syntax) : Sort u := α`, `@[reducible] def outParam (α : Sort u) : Sort u := α`, and `semiOutParam` like `outParam`). Otherwise the domain is kept and checked literally. The C++ kernel strips by name alone, which is unsound when the name means something else: with `def optParam (α β : Type) : Type := β` declared in an environment without the prelude, it accepts `inductive T | mk : optParam A B → T` and generates a recursor whose minor premise takes an `A` for a constructor field of type `B`; lean4lean keeps `optParam A B` in the constructor and the recursor (`Tests/TypeAnnotationWrappers.lean` checks both behaviours). Both kernels type-check the complete constructor and header types before stripping anything, so an application of an undeclared wrapper name is rejected by both. The constructed recursor therefore differs only on environments that declare one of the four names with another definition, and only there can a decision differ (for example, the universe check of a field reads the stripped domain in the C++ kernel); on every environment in which the wrappers are the prelude's, or are not used, the two kernels strip the same applications and make the same decisions. The lookup only happens when a binder domain is headed by one of the four names. Each strip is justified from the definition looked up at that point (`TypeAnnotationWrappers.of_env`), so the verification needs no invariant on how these names are declared, and the empty environment satisfies `VEnvs.WF` (`VEnvs.WF.empty`).

## Audit of the executable changes of the verified inductive checker

Every behavioural change made to the executable relative to `master` (`Lean4Lean/TypeChecker.lean`, `Inductive/Add.lean`, `Inductive/Reduce.lean`, `Primitive.lean`, `Quot.lean`, `EquivManager.lean`, `Replay.lean`, `Expr.lean`, `ExprUniverses.lean`, `WHNFCacheKey.lean`, `Main.lean`; `Environment.lean`, `Environment/Basic.lean` and `Level.lean` are unchanged). Class (i): same decisions and same constructed terms as the C++ kernel (justification given); (ii): divergence documented above before this audit; (iii): divergence found by the audit and documented above.

| change | class | action |
|---|---|---|
| cache modes (`CacheMode` in `FuelConfig`; scoped: `State.leaveScope`, `withFreshId`, bodies always under a binder in `isDefEqLambda`/`isDefEqForall`; global: caches kept, binders as `is_def_eq_binding`) | (iii) | entry rewritten; the default scoped mode can reject a term the C++ kernel accepts, whose acceptance is the non-local one; the global mode matches the C++ kernel and needs a `GlobalCacheLicense`, of which no inhabitant exists; both modes are verified |

### What the differential replay establishes

`scripts/differential-replay.sh`, run in CI, replays with `--differential`: each declaration goes to lean4lean and to the C++ kernel (`Kernel.Environment.addDecl` of the pinned toolchain, no heartbeat limit) on the same environment, the one lean4lean has built so far, and when both accept, the constants the declaration adds (the declared names; for an inductive block its types, constructors, recursors and nested auxiliary recursors; the four quotient constants) are compared under `==`. The corpus is `Init` with all its imports, i.e. every `Init.*` module, replayed from the empty environment (`--fresh --exact Init`, 63936 declarations), and each module of `Lean4Lean.Tests` replayed into its imports (1027 declarations). Result at the time of writing: 64963 declarations, 64963 agreements, no lean4lean-only rejection, no kernel-only rejection, no constructed-term mismatch.

It establishes, for this corpus: lean4lean in its default scoped cache mode accepts every declaration the C++ kernel accepts (so none of the class (i) changes above, and none of the entries that claim no decision change, changes a decision on it, and the scoped mode's divergence does not arise in it); the C++ kernel accepts every declaration lean4lean accepts, in lean4lean's own environment; and every constructor and recursor lean4lean generates (types and rules) is the C++ kernel's, constant by constant, not only the elaborated module's copy that the replay's final agreement check compares against.

It does not establish: (1) agreement on rejections, since every declaration of the corpus was accepted by the C++ kernel when elaborated; rejection behaviour rests on the tests (`Tests/KernelHardening.lean`, `Tests/SortEquationRejection.lean`, `Tests/CacheScope.lean`, `Tests/TypeAnnotationWrappers.lean` and others) and on the proofs; (2) anything about the divergences that arise only on environments the corpus does not contain: a redefined type-annotation wrapper, the cache-scope seed of `Tests/CacheScope.lean` (built inside the test, not declared in the module), structure eta at a sort that is neither always nor never zero; (3) anything about the 77 unsafe and 521 partial constants of `Init`, which the replay skips; (4) anything about `Std`, `Lean` or `Lake`, which are not in the corpus (`--fresh` on modules importing `Lean` fails, digama0/lean4lean#17); (5) anything about the global cache mode, which cannot be run; (6) agreement with a later C++ kernel: the comparison is with the pinned toolchain's, which does not have the recursor-type check of leanprover/lean4#14808 that lean4lean performs.
